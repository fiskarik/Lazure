# Формат данных и порядок обработки

Шаблон хакатона предусматривает этот файл для спецификации протокола. Для «Нейро-стенографиста» протоколом служат формат входных данных, формат JSON-вывода и правила, по которым из модели получаются реплики.

## Цели

- Выдавать расшифровку, которую можно автоматически сравнить с эталоном (WER, диаризация, временные метки).
- Никогда не подменять результат модели: если речь не найдена или модели отсутствуют, экспортируется пустой массив, а не придуманный текст.

## Входные данные

- Аудиофайл любого формата, который декодирует `MediaCodec` на устройстве: WAV, MP3, M4A/AAC, OGG/Opus, FLAC и т. д. Моно или стерео, любая частота дискретизации.
- Импорт: «Импорт» на главном экране или в архиве → системный выбор файла. Файл копируется в приватное хранилище приложения.
- Запись из приложения: экран «Запись», WAV 16 кГц моно (`AudioRecord`, источник `VOICE_RECOGNITION`, системный AEC, если он есть на устройстве).
- Перед обработкой сигнал сводится в моно и передискретизируется в 16 кГц.

## Формат JSON-вывода

```json
{
  "transcript": [
    { "speaker_id": "speaker_1", "start_ms": 1250, "end_ms": 4380, "text": "Добрый день!" }
  ]
}
```

| Поле | Тип | Правило |
|---|---|---|
| `transcript` | array | Единственный ключ верхнего уровня. Реплики упорядочены по `start_ms` |
| `speaker_id` | string | `speaker_1`, `speaker_2`, … в порядке первого появления в разговоре |
| `start_ms` | integer | Метка первого токена реплики, мс от начала файла |
| `end_ms` | integer | Метка последнего токена реплики + 80 мс (см. ниже), всегда `> start_ms` |
| `text` | string | Текст с пунктуацией GigaAM v3. Если пользователь исправил реплику, экспортируется исправленный текст |

Переименование говорящего в интерфейсе («Мама», «Барсик») меняет только отображаемое имя. В JSON остаётся стабильный `speaker_id`.

## Правила формирования реплик

1. **Токены.** GigaAM v3 CTC выдаёт токены и их временные метки внутри VAD-сегмента. К меткам прибавляется начало сегмента.
2. **Конец реплики** — метка последнего токена + 80 мс. GigaAM CTC ставит метку ближе к концу токена, поэтому это правило ближе к реальному концу речи, чем конец сегмента VAD (см. `tools/bench/token_timing_check.py`).
3. **Говорящий** определяется для слова (кусочки BPE и знаки препинания идут за своим словом) по предложению, в которое оно входит. Предложение режется по знакам конца предложения, паузам > 0,35 с, точкам смены говорящего диаризатора и тире диалога в выводе GigaAM. Каждой резке нужно подтверждение эмбеддингами CAM++.
4. **Реплика** — подряд идущие слова одного говорящего. Новая реплика начинается после паузы > 1 с, при длине > 30 с или если между словами вклинился другой говорящий (≥ 3 токена или ≥ 0,3 с его речи).
5. **Склейка.** Соседние реплики одного говорящего с паузой < 0,6 с объединяются, если общая длина не превышает 30 с и между ними не начиналась реплика другого человека.
6. **Наложения.** Реплики разных говорящих могут пересекаться по времени (перебивания, одновременная речь). Реплики одного говорящего не пересекаются никогда. Реплика помечается как «Перебивание», если она пересекается с репликой другого говорящего больше чем на 250 мс или с участком одновременной речи (≥ 0,3 с по pyannote): больше чем на 250 мс либо больше чем на 100 мс, если диаризатор слышал там этого говорящего. В JSON формат не меняется.

## Установление и завершение обработки

Состояния записи: `awaiting_asr` → `queued` → `processing` (0–100 %) → `completed` | `failed` | `cancelled`.

После `completed` в карточке записи показываются время обработки и RTF (время обработки / длительность аудио).

## Синхронизация

Плеер и расшифровка синхронизированы по `start_ms`/`end_ms`. Нажатие на реплику перематывает аудио, текущая реплика подсвечивается во время воспроизведения.

## Ошибки и восстановление

- Если модели речи отсутствуют в APK, запись переходит в `failed`, и интерфейс сообщает об этом.
- Если процесс убит во время обработки, после перезапуска статус становится `failed`, и запись можно обработать заново.
- Если процесс убит во время записи, WAV-заголовок восстанавливается (он обновляется каждые ~2 с), запись регистрируется как «Восстановленная запись» и обрабатывается.
- Перед записью файла экспорт проверяет порядок и корректность меток (`TranscriptExport.validate`).

## Совместимость

- Android 7.0+ (minSdk 24), целевой API 36. ABI: `arm64-v8a` (телефоны) и `x86_64` (эмулятор).
- Формат JSON совпадает с примером из задания; проверяется в `TranscriptExportTest`.

## Пример

Импорт файла `cats_dialog_1.ogg` → обработка → «Экспорт JSON» → `cats_dialog_1.json`:

```json
{
  "transcript": [
    { "speaker_id": "speaker_1", "start_ms": 320, "end_ms": 2140, "text": "Ты опять съел мою еду?" },
    { "speaker_id": "speaker_2", "start_ms": 2380, "end_ms": 3010, "text": "Нет." },
    { "speaker_id": "speaker_1", "start_ms": 3150, "end_ms": 5600, "text": "Тогда кто оставил крошки у миски?" }
  ]
}
```

Это иллюстрация формата, а не результат реального прогона.
