# Методика и результаты тестирования

## Метрики

Эксперты оценивают точность транскрибации (WER), диаризации, временных меток и время обработки (RTF). Мы считаем те же величины скриптом [`tools/eval/evaluate.py`](../tools/eval/evaluate.py). Ему нужны только стандартная библиотека Python и JSON в формате конкурса с обеих сторон.

| Метрика | Что измеряет |
|---|---|
| **WER** | Ошибки слов во всём разговоре. Текст в нижнем регистре, `ё → е`, без пунктуации |
| **WER_raw** | То же без нормализации: показывает, сколько дают пунктуация и регистр |
| **cpWER** | WER по говорящим при лучшем сопоставлении: учитывает и распознавание, и приписывание слов не тому говорящему |
| **DER** | (пропуск речи + ложная речь + путаница говорящих) / длительность эталонной речи; кадры 10 мс, коллар 0,25 с |
| **start/end MAE** | Средняя абсолютная ошибка начала и конца реплики для пар с IoU ≥ 0,5 |
| **within500** | Доля таких реплик, у которых обе границы точнее 500 мс |
| **RTF** | Время обработки / длительность аудио. Время показывается в карточке записи и пишется в logcat (`RecordingProcessor`) |

Порядок прогона:

1. Положите эталонные JSON в `refs/`. Имена файлов должны совпадать с именами аудио.
2. Импортируйте аудио в приложение и дождитесь обработки.
3. Экспортируйте JSON каждой записи в `exports/`.
4. Внесите время обработки из карточки в `timing.csv` (`file,audio_sec,processing_sec`).
5. Запустите:

   ```bash
   python3 tools/eval/evaluate.py --ref refs/ --hyp exports/ --timing timing.csv --csv artifacts/test-results/results.csv
   ```

## Автоматические тесты

| Набор | Команда | Последний результат |
|---|---|---|
| Unit-тесты (JVM + Robolectric) | `./gradlew :app:testDebugUnitTest` | **54 теста, 0 ошибок**, 1 пропущен (`SpeechPipelineJvmTest` без моделей) — 2026-11-08 |
| Самотест скрипта оценки | `python3 -m unittest discover -s tools/eval` | **10 тестов, 0 ошибок** |
| Сборка | `./gradlew :app:assembleDebug`, `:app:assembleRelease -Plazure.abis=arm64-v8a` | Обе собираются; release подписан, классы sherpa-onnx не переименованы R8 |
| Инструментальные тесты | `./gradlew :app:connectedDebugAndroidTest` | Компилируются. Последний прогон на эмуляторе ARM64 / API 33 — до текущих правок (9 тестов, 0 ошибок); новый тест миграции 10→11 на устройстве ещё не запускался |

Что покрывают unit-тесты:

- `TranscriptExportTest` — точная схема JSON, пустой экспорт, отказ на неупорядоченных или некорректных метках;
- `DiarizationEvidenceTest` — исключительная речь и «слышали одновременно» на раскладке реплик реальной записи с перебиваниями;
- `RecordingProcessingStatusTest` — допустимые переходы статусов;
- `RecordingAiTest` — таймкоды и поиск фрагментов для вопросов к LLM;
- `ThinkFilterTest`, `LlamaRuntimeTuningTest` — подготовка ответа и параметров LLM;
- `PinRepositoryTest`, `ColorContrastTest`, `HomePolishTest`, `MarkdownParserTest` и др. — PIN, контраст темы, вёрстка, разметка.

`SpeechPipelineDeviceTest` (инструментальный) прогоняет пайплайн на файлах из `files/eval` устройства и пишет результат в logcat (`SPEECH_EVAL`).

`SpeechPipelineJvmTest` запускает **настоящий `SpeechPipeline` приложения на компьютере**: VAD, GigaAM, диаризацию, уточнение говорящих и пометку перебиваний. Он работает на Linux-сборке sherpa-onnx, без телефона. DTLN и MossFormer2 работают только на Android и в нём пропускаются. Для каждого WAV тест печатает реплики и пишет JSON в `$LAZURE_EVAL_DIR/out` для `tools/eval/evaluate.py`.

1. Скачайте JNI-библиотеку:

   ```bash
   curl -L https://github.com/k2-fsa/sherpa-onnx/releases/download/v2.0.1/sherpa-onnx-v2.0.1-linux-x64-jni.tar.bz2 | tar xj
   ```

2. Положите модели в каталог со структурой `assets/` (`models/asr-gigaam-v3-ru/…`, `models/vad/…`, `models/diar-segmentation/…`, `models/diar-embedding/…`).
3. Подготовьте WAV 16 кГц моно:

   ```bash
   ffmpeg -i in.m4a -ac 1 -ar 16000 eval/in.wav
   ```

4. Запустите тест:

   ```bash
   LAZURE_SHERPA_JNI_DIR=$PWD/sherpa-onnx-v2.0.1-linux-x64-jni/lib LAZURE_MODELS_DIR=/path/to/assets LAZURE_EVAL_DIR=/path/to/eval ./gradlew :app:testDebugUnitTest --tests '*SpeechPipelineJvmTest*' --rerun -i
   ```

## Результаты на собственных данных

### Диаризация: синтетический бенчмарк

Данные — [`tools/bench`](../tools/bench): четыре русских диалога с известной разметкой, голоса — одна TTS-модель со сдвигом высоты. Такие голоса похожи сильнее, чем голоса двух реальных людей. Метрика — доля эталонной речи с правильным говорящим при лучшем сопоставлении. Прогон на эмуляторе ARM64.

| Диалог | До уточнения говорящих | После |
|---|---|---|
| `rapid3` — 3 голоса, паузы 0,05–0,3 с, односложные ответы | 82,0 % | 94,3 % |
| `mixed3` | 81,5 % | 90,4 % |
| `dialog2` — 2 голоса | — | 97,4 % |
| `long2` — длинные реплики | — | 99,6 % |
| **Всего** | **91,4 %** | **96,6 %** |

На распознанной речи говорящий указан верно в 98,7 % случаев. Остаток — пропущенные односложные ответы и реплики 0,4–0,7 с.

### Временные метки: правило конца реплики на реальной GigaAM

[`tools/bench/token_timing_check.py`](../tools/bench/token_timing_check.py) собирает три русских диалога с известными границами реплик: фразы espeak-ng двумя голосами и реальная запись `example.wav` из комплекта модели, паузы 0,15–2 с. Через них прогоняются Silero VAD с параметрами приложения и GigaAM v3 CTC (sherpa-onnx 2.0.1, как в приложении). Говорящие берутся из эталона, поэтому измеряется только время. Учитываются 24 правильно распознанные реплики.

| Правило | Смещение | MAE | В пределах 0,5 с |
|---|---|---|---|
| Начало = метка первого токена | −0,23 с | 0,24 с | 100 % |
| Конец = метка последнего токена + 80 мс (**в приложении**) | −0,09 с | **0,38 с** | 75 % |
| Конец = следующий токен или конец речи по VAD | +0,52 с | 0,54 с | 50 % |

Голоса синтетические, поэтому абсолютные цифры ориентировочные. Этот замер нужен для выбора правила.

### Перебивания и разметка говорящих (2026-11-08)

**Проблема.** На реальной 22-секундной записи (два человека по очереди, два перебивания) приложение выдавало 3 «говорящих». Реплики перебивающего («Ты опять проспал?», «Автобус не приехал?», «Серьёзно?») были приписаны перебитому, перебивания не отмечались.

**Причина** найдена прогоном настоящего пайплайна через `SpeechPipelineJvmTest`. pyannote оба наложения видит (вероятность одновременной речи 0,97 и 0,92), но:
1. id перебивающего встречается только в наложениях, поэтому «чистота» id считалась по словам перебитого;
2. короткие реплики одного человека (сходство CAM++ 0,23) не объединялись;
3. наложение 0,54 с отсекалось порогом 0,6 с.

Исправления описаны в [ARCHITECTURE](ARCHITECTURE.md).

**Набор:** эта запись (приблизительная разметка: границы по pyannote, текст и говорящие по смыслу) и 6 диалогов, смонтированных из **живой речи** с перебиваниями 0,3–0,9 с. Два диалога собраны из голосов этой же записи, четыре — из публичных записей sherpa-onnx ([`tools/bench/make_overlap_dialogs.py`](../tools/bench/make_overlap_dialogs.py)). В двух из них голоса похожие: один диктор с изменённой высотой. Разделение MossFormer2 не используется.

| Файл | cpWER до → после | DER до → после | Говорящих (эталон 2) | Отмечено перебиваний |
|---|---|---|---|---|
| Реальная запись с перебиваниями | 48,8 % → **16,3 %** | 19,7 % → **12,6 %** (путаница 7,6 % → **0 %**) | 3 → **2** | 0 → **4** |
| Голоса записи, перебивания 60 % | 66,7 % → **50,0 %** | 27,6 % → **14,5 %** | 3 → **2** | 0 → 1 |

| Публичные голоса A+C | 30,1 % → 31,1 % | 7,1 % → 8,0 % | 2 → 2 | 0 → 0 |
